双网关统一域名架构说明书

一个域名 a.c.xxx → 有 v6 走 DDNS 直连，无 v4 走 Cloudflare 穿透 → 收敛到 FPK 入口容器

一、架构总览

客户端只记一个域名，DNS 层自动判断地址族：返回 AAAA 走网关A 直连 IPv6；只剩 A 走网关B 经 CF 边缘穿透回源。两条链路最终都收敛到 FPK 入口容器做反代收口。

二、DNS 分流逻辑

关键在 DNS 记录的"自动分流"：a.c.xxx 同时挂 AAAA 和 A 两条记录，客户端操作系统按自身协议栈优先选择：

DNS 记录 值 对应链路 说明
a.c.xxx AAAA NAS 公网 IPv6 网关A · DDNS 直连 DDNS 脚本实时同步，客户端直接拿到 NAS v6 地址，零转发延迟
a.c.xxx A Cloudflare 隧道指向的 IP 网关B · CF 穿透 NAS 没有公网 IPv4，所以这条走 CF 边缘节点 + knock 隧道回源
为什么能自动分流？ 现代操作系统（Windows 10+/macOS 10.15+/Linux glibc）的 happy-eyeballs 算法会同时探测 AAAA 和 A，哪个通哪个优先。没有 IPv6 的网络（纯 v4）会直接跳过 AAAA，走 A 记录 → CF 穿透兜底。

三、网关A · DDNS IPv6 直连（主路径）

🎯 目标
NAS 的公网 IPv6 地址直接暴露，客户端 v6 网络直连，不经过任何第三跳。
⚡ 优势
延迟最低（1~10ms）、带宽无损、不依赖任何外部服务。

3.1 前置条件

  • 路由器已拿到 IPv6 前缀（运营商分配 /60 或 /64）
  • NAS 获得一个可被外部路由的 公网 IPv6 地址（不是 ULA fdxx::）
  • 域名 DNS 提供商支持 DDNS 更新（Cloudflare / 阿里云 / 腾讯云等）

3.2 配置步骤

  1. 在 OpenWrt 路由器上启用 IPv6 防火墙入站规则，放行 NAS 的目标端口（通常是 FPK 的 80/443 或服务端口）
  2. 部署 DDNS 客户端。OpenWrt 自带 luci-app-ddns，用它把 NAS 的 IPv6 同步到 a.c.xxx 的 AAAA 记录 
    # OpenWrt /etc/config/ddns 示例
config service 'v6_ddns'
    option enabled '1'
    option interface 'wan6'
    option use_ipv6 '1'
    option ip_source 'web'
    option ip_url 'https://api64.ipify.org'
    option update_url 'https://api.cloudflare.com/client/v4/zones/{zone_id}/dns_records/{record_id}'
    ...
  3. 在 NAS 上用 curl -6 ifconfig.me 验证公网 v6 可达
  4. DNS 服务器上 dig AAAA a.c.xxx 确认 AAAA 记录已生效

四、网关B · Cloudflare 隧道 IPv4 穿透（兜底）

🎯 目标
NAS 没有公网 IPv4，通过 Cloudflare 边缘节点 + knock 隧道回源，让纯 v4 客户端也能访问。
🛡️ 优势
不暴露源站真实 IP、自带 DDoS/CDN 防护、配合 knock 隧道安全认证。

4.1 前置条件

  • 域名已托管到 Cloudflare（或其他支持 Tunnel 的 DNS 服务商）
  • NAS/路由器上能运行 cloudflared 或 knock 隧道客户端

4.2 配置步骤

  1. Cloudflare Dashboard → Zero Trust → Tunnels → 创建隧道，拿到 cloudflared token
  2. 在 OpenWrt 上安装 cloudflared（或使用 hebing / knock 隧道客户端），启动隧道 
    # cloudflared 典型启动命令
cloudflared tunnel run --token {your-cloudflared-token}
  3. 在 Cloudflare Dashboard 里配置 Public Hostname：a.c.xxx → http://localhost:7999（假设 knock 隧道监听 7999）
  4. DNS 自动生成一条 A a.c.xxx → 192.0.2.1（Cloudflare 边缘保留 IP），纯 v4 客户端会命中这条
  5. 验证：curl -4 https://a.c.xxx 应该能通过 CF 边缘回源到 knock 隧道

五、DNS 记录总表

在 Cloudflare DNS 面板上最终应看到：

类型名称值代理状态TTL
AAAAaNAS 公网 IPv6仅 DNS（灰色云朵）1 min（DDNS 要求）
AaCloudflare Tunnel 自动生成橙云代理Auto
注意：AAAA 记录必须关闭 Cloudflare 代理（灰云），否则 v6 请求也会被 CF 边缘拦截，直连路径废掉。只有 A 记录走橙云代理让 CF 处理。

六、FPK 入口容器收口

两条链路最终都到达同一套 FPK 入口容器（反向代理 + 安全门），它负责：

  • 统一 TLS 终止 / 证书管理（ACME 自动续签）
  • 反向代理到后端实际服务
  • 访问控制 / knock 认证 / 限速

路径：

客户端 → a.c.xxx → { FPK 入口 :80/443 } → 后端服务

七、OpenWrt 侧 hebing 的角色

本仓库的 hebing 服务包跑在 OpenWrt 路由器上，承担：

组件作用
hebing 二进制网关服务，监听指定端口，转发请求到 FPK 或 knock 隧道
/etc/init.d/hebingprocd 管理，respawn 自动拉起崩溃实例
/etc/config/hebingUCI 配置：端口、监听地址、数据目录
knock 隧道配合 Cloudflare 兜底路径做 v4 穿透

7.1 安装

# 在路由器上
opkg install /tmp/hebing_0.1.0-1_x86_64.ipk
/etc/init.d/hebing status   # 查看 procd 状态
/etc/init.d/hebing enable   # 开机自启

7.2 常用配置

# 改监听端口
uci set hebing.main.listen_port='8443'
uci commit hebing
/etc/init.d/hebing restart

八、故障排查

场景 1：v6 直连不通，v4 CF 穿透正常

  1. 路由器上 ping -6 ipv6.google.com 确认 IPv6 本身通
  2. dig AAAA a.c.xxx 确认 AAAA 记录正确
  3. 临时关 OpenWrt IPv6 防火墙：fw4 flush 或 /etc/init.d/firewall restart 看是否防火墙拦截
  4. 确认 NAS 的 IPv6 不是 ULA（fd 开头的都是内网，不可路由）

场景 2：v4 CF 穿透不通，v6 正常

  1. Cloudflare Zero Trust → Tunnels → 查看隧道连接状态是否 Healthy
  2. cloudflared tunnel info <tunnel-id> 看日志
  3. 本地 curl http://localhost:7999 确认 knock 隧道本地端口正常
  4. DNS 的 A 记录是否橙云代理打开

场景 3：全部不通

  1. hebing 服务状态：/etc/init.d/hebing status
  2. 重启服务：/etc/init.d/hebing restart
  3. 看日志：logread | grep hebing
  4. 端口被占？netstat -tlnp | grep 8080
